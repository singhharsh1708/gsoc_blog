GSoC 2026 Weeks 1–2 — Finishing the IMEX Tableau Refactor

May 31, 20266 min readGSoC

The coding phase has begun. These first two weeks were about closing the loop on the foundation — making the generic IMEXTableau stepper behave identically to the bespoke kernels it replaces, before I trusted it with any new method. By the end of the fortnight, it had earned that trust: the first ARS IMEX-RK schemes landed as tableau-only changes.

Picking up from community bonding

In the Week 0 post I laid out the plan: collapse the per-family perform_step! kernels into a single generic dispatch driven by a Butcher tableau, then use that foundation to add new methods cheaply. Weeks 1–2 were the unglamorous but essential half of that — hardening the abstraction so it's a reliable base, not a leaky one.

Hardening the SDIRK/IMEX stepper

The risk with a generic kernel is subtle behavioral drift: a method that used to converge in n Newton iterations now takes n+1, or an embedded error estimate is computed slightly differently and adaptivity changes. Most of this cycle was hunting down and closing those gaps.

  • #3650: Unified error estimation under a single dispatched calculate_error_estimate!, so embedded-pair error control lives in one place instead of being re-derived per family.
  • #3651: Migrated CFNLIRK3 into the ESDIRKIMEX tableau form.
  • #3654: Forced type specialization of the ESDIRK*L2SA tableau dispatches to keep them zero-allocation and type-stable.
  • #3656: Migrated the ABDF2 Euler cache onto ESDIRKIMEXCache and dropped the legacy implicit-Euler caches.
  • #3661: Added a tableau embedded-pair consistency test for adaptive SDIRK/ESDIRK methods — a guardrail so future tableau edits can't silently break adaptivity.
  • #3662: Fixed the ESDIRK659L2SA embedded coefficients so adaptive solves actually work (#3659).
  • #3668: Added a generic stage-predictor menu for ESDIRK methods, so initial guesses for the implicit stages can be chosen consistently across the family.
  • #3670: Fixed linsolve propagation through the nonlinear-solver algorithm so the configured linear solver actually reaches the inner Newton solve.

Reusing the W matrix as a Jacobian

A satisfying optimization this cycle: teaching the nonlinear solver to reuse work the ODE integrator already does. The implicit RK stages factor a W = I − γΔt·J matrix every step; the embedded nonlinear solve was recomputing Jacobian information it could have borrowed straight from the integrator.

Why this matters

The Jacobian is usually the most expensive object in an implicit solve. If the integrator already holds an up-to-date W, handing it to the nonlinear solver as an analytic Jacobian avoids a redundant evaluation per step — free performance with no change to the math.

  • #3693: Made NonlinearSolveAlg reuse the ODE solver's W matrix as an analytic Jacobian (#2757).
  • #3703: Extended the modified-Newton path to the nlstep/DAE/out-of-place code paths (#3696).

The payoff: first ARS methods land

With the foundation solid, the very end of the fortnight delivered the first real dividend. The Ascher–Ruuth–Spiteri (ARS) IMEX-RK schemes — workhorses for convection–diffusion–reaction problems where the stiff part is treated implicitly and the rest explicitly — went in as a pair of Butcher tableaus over the shared kernel. No new perform_step!, no new cache, no new bug surface.

Challenges this cycle

  • Behavioral parity: keeping the generic stepper numerically identical to the old bespoke methods meant a lot of careful before/after comparison on convergence and step-count, not just "does it run."
  • Tolerance sensitivity: the embedded-pair consistency test (#3661) exists precisely because small dispatch changes can perturb adaptive error estimates — and a few existing tests turned out to be quietly over-tight.
  • Type specialization: #3654 was a reminder that "generic" and "zero-allocation" pull against each other — the ESDIRK*L2SA dispatches needed forced specialization to stay type-stable.

Goals for the next two weeks

  • Expand the IMEX-RK family on the now-stable stepper — IMEX-SSP and the Boscarino–Russo BHR schemes.
  • Begin the multirate deliverable: get the first explicit multirate solvers into OrdinaryDiffEq.jl.
  • Keep the convergence and zero-allocation suites green across every migration.

Closing thoughts

This was the half of the project that doesn't make for flashy screenshots, but it's the half everything else rests on. Watching ARS222/232/443 drop in as pure tableau definitions at the end of the fortnight was the proof the refactor was working as designed — adding a vetted method went from "write and debug a kernel" to "write down a tableau and a test." Next up: the rest of the IMEX family, and the first multirate solvers.
