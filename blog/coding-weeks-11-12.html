GSoC 2026 Weeks 11–12 — Fixing It Upstream, and a Merge Wave

August 4, 202615 min readGSoC

A note first: this cycle isn't over. I'm writing on August 4, before the fortnight closes, so this is a mid-cycle update rather than a finished retrospective. Two things define it so far: the fix for the bug I spent most of Weeks 9–10 chasing went upstream, into NonlinearSolve.jl, rather than being worked around locally — alongside a second, unrelated upstream fix in SciMLOperators.jl — and a batch of long-open pull requests landed all at once between July 31 and August 4.

Fixing it at the interface, not around it

Last cycle I said the polyalgorithm fix belonged upstream rather than in a special case inside OrdinaryDiffEq. The upstream half merged on July 31:

  • NonlinearSolve.jl #1115: Reset force_stop/retcode in the polyalgorithm reinit!, plus get_u/get_fu accessors. InternalAPI.reinit!(::NonlinearSolvePolyAlgorithmCache) reset current, nsteps, stats and total_time but left force_stop and retcode at their converged values, and CommonSolve.step! guards on force_stop — not_terminated(cache) = !cache.force_stop && cache.nsteps < cache.maxiters — reading it off the polyalgorithm cache. The @generated solve! method drives the subcaches directly and is unaffected, so this only bites a step!-driven loop — which is exactly how an implicit ODE solver runs a nonlinear solve across a step. Released as NonlinearSolveBase 2.39.0.

With 2.39.0 out, #3959 — the OrdinaryDiffEq half, promised last cycle as consumer-side-only — merged on August 1 with the compat floor raised to "2.39". The five polyalgorithm-unsafe inner-cache reads it had to route through the upstream accessors were the resize length check, the stale-W rhs rescale from #4028, both compute_step! paths, and the nlstep build_solution. No local workaround remains.

A second upstream fix landed the same day, in a different repository and for a different bug:

  • SciMLOperators.jl #416: Fixed update_coefficients! for operators built with only an out-of-place update_func. MatrixOperator is immutable, but the in-place path assigned L.A = L.update_func(...), so every call threw setfield!: immutable struct of type MatrixOperator cannot be changed. Issue #409 named only MatrixOperator; the same pattern sat unreported a second time in BatchedDiagonalOperator, where DiagonalOperator(u::AbstractMatrix; update_func = ...) crashed identically. The PR fixes both, computing the new value out-of-place and copyto!-ing it into existing storage when that storage is mutable.
The stack trace is not the owner

The error surfaced in OrdinaryDiffEq but the invariant lived in NonlinearSolve. The layer a failure shows up in is rarely the layer that owns the rule being broken. Fixing upstream is slower — you wait on someone else's review and release — but the alternative is a workaround that quietly becomes your package's problem forever, and that every other consumer rediscovers for themselves.

The merge wave

Most of the wave appeared here already — Weeks 9–10 covered the order-4 multirate method, the NonlinearSolveAlg cluster, the mass-matrix chain and the ExplicitTaylor FSAL fix, all of which merged across July 31, August 1, August 3 and August 4. Four PRs in it have never appeared in this devlog, and all four had been open well before this cycle started.

  • #3241: Sixteen ES-DG-optimized 3S* low-storage Runge-Kutta methods from Al Jahdali et al. (2022) — eight advection-optimized (AlJahdaliAdv3S*), eight vortex-optimized (AlJahdaliVor3S*), orders 2 through 5, fixed timestep only as in the paper. Merged July 31, closing issue #2903.
  • #3683: Folded RK46NL into the generic LowStorageRK2N dispatch. Master's consolidation had given nine 2N methods a shared LowStorageRK2NAlgorithm union and alg_cache; RK46NL was the one plain-2N method left out, still carrying bespoke caches and four hand-unrolled initialize!/perform_step! methods. Merged August 1.

Neither adds new stepping code. #3241 is pure coefficient data, running through the existing LowStorageRK3SAlgorithm union and _lowstorage_3s_tableau dispatch exactly like the ParsaniKetcheson family, so what needed proving was that the numbers were right: the tableaus were reconstructed in BigFloat and checked against the rooted-tree order conditions directly, all satisfied at the claimed order and the order-(p+1) conditions properly violated. #3683 has one consequence worth stating plainly rather than burying — williamson_condition is now the struct's fourth field, so positional construction takes four arguments and RK46NL(stage_limiter!, step_limiter!, thread) no longer resolves.

The real win was what didn't get written

A late rework of #3241 folded its hand-written per-method alg_cache definitions into the shared dispatch, taking 705 lines back off the branch, with end states bit-identical before and after for all sixteen methods, in-place and out-of-place. #3683 removes a net 134 lines of source. Sixteen new methods and a migration, and not one new perform_step! between them — code that doesn't exist can't drift out of sync with the family it belongs to.

The other two are stochastic-solver fixes, and they are the layering story told from the other end: in both, an object constructed one layer down arrives at the solver in a shape the solver never thinks to check. #3468 gets a noise process whose rng lives behind a wrapper; #3763 gets an increment prototype whose sparsity was inherited from a matrix that means something else entirely. Both merged August 1:

  • #3468: Fixed SROCK2 with NoiseWrapper and with non-square noise, closing issues #3188 and #3170. Single-channel non-square noise was routed into the diagonal code paths by length(W.dW) == 1 shortcuts — a MethodError out of place, a DimensionMismatch in place, across SROCK2, SROCKEM, SROCKC2, KomBurSROCK2 and TangXiaoSROCK2. Separately the NoiseWrapper case died with FieldError: type NoiseWrapper has no field rng, because the χ draw read W.rng directly; an rng(W) helper now walks to the wrapped source, recurses through nested wrappers, and falls back to the global generator for processes that replay a recorded path and have none — which also un-breaks SROCK2 with NoiseGrid. The eq. (17) cross terms went in too.
  • #3763: Made rand_prototype dense when the noise_rate_prototype is sparse. _sde_init built the Wiener increment prototype as false .* noise_rate_prototype[1, :], a SparseVector — the wrong shape for the object, since the sparsity pattern of g records which states a channel drives, not which channels are idle, so every column still draws an increment and dW fills in completely on the first step anyway. That prototype breaks two solvers two ways. W2Ito1 fails outright — its cache keeps _dW, _dZ and chi1 under one randType field and builds _dZ = zeros(eltype(ΔW), 2) unconditionally, so with a sparse dW there is no applicable constructor. RKMilGeneral fails silently, deriving its Lévy area dZ from the increment prototype.
The questions I hadn't asked

On #3468 my mentor pushed on the questions I had not asked myself — whether the algorithm is even correct for non-diagonal noise, whether it needs Lévy areas, and whether the paper claims weak order 2 in that setting. Answering all three out of Abdulle et al. was a real part of the work on that PR, and more of it than the rng helper that the issue report actually pointed at.

The same bug, one sublibrary over

And then, today:

  • #4112: Fix NewmarkBeta crashing with polyalgorithm nonlinear solvers — opened August 4, still open as I write. nlsolve is a public keyword on both NewmarkBeta and GeneralizedAlpha; the default NewtonRaphson works, as does any algorithm whose cache steps in place. Everything else crashed on the first step, with type NonlinearSolvePolyAlgorithmCache has no field p or type NonlinearSolveNoInitCache has no field p.

That is the same bug class as #3859, which #3959 fixed for NonlinearSolveAlg, showing up in a different sublibrary. The mechanism is familiar: the integrator cache was using the inner nonlinear cache as its own storage, building a fresh NewmarkDiscretizationCache each step and recovering its three DiffCache AD buffers by reaching into nlcache.p — and a cache that keeps its parameter object somewhere other than a field called p has nothing to reach into. The discretization state now lives on the integrator cache and is refreshed in place per step. That alone isn't sufficient either: NonlinearSolveBase's @generated solve! specialization for NonlinearSolvePolyAlgorithmCache never writes the parent's retcode back, so it stays at ReturnCode.Default and a caller driving the cache through solve! has to read the returned solution instead of the cache. Hitting the same cache assumption in a second sublibrary is a fair sign it was systemic rather than local.

Challenges this cycle

  • A moving target under review: master restructured the low-storage family while #3241 sat in the queue, so the PR needed a late rework to consolidate its per-method alg_cache definitions into the shared dispatch — and then a demonstration that the consolidated version was bit-identical to what it replaced, for all sixteen methods, before it could land.
  • Bugs that don't stay fixed in one place: #4112 turned up on the day I would otherwise have called the polyalgorithm problem closed.

Goals for the next two weeks

  • Land #4112, whose second half works around that missing retcode write-back on the caller side.
  • Get #3798 — out-of-place NonlinearSolveAlg W-reuse with SimpleNonlinearSolve solvers — over the line; open since June 29, now the oldest thing on my list.

Closing thoughts

Since this is a mid-cycle post, I'll resist drawing a conclusion the cycle hasn't earned — #4112 is still open. What I can say already is that most of the effort went into deciding where a fix belonged rather than what it should say. Working around a broken invariant downstream is the faster path on the day, and also how a package accumulates defensive code nobody can later explain. The merge wave made a quieter point — #3683 removed more source than it added, #3241's late rework deleted 705 lines of duplication from its own branch, and sixteen new methods arrived without a single new perform_step!. The work I'd point at from this cycle is the part where the abstraction was already right and the job was making the code admit it.
