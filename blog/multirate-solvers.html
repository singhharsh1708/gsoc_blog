Building Multirate Solvers: MREIL, MIS & MRGARK

📅 May 7, 2026🕐 13 min readNumerical Methods

Many physical systems exhibit dynamics on widely separated time scales. In atmospheric modeling, acoustic waves propagate orders of magnitude faster than advective transport. In circuit simulation, fast switching transients coexist with slow thermal dynamics. Using a single time step dictated by the fastest scale wastes enormous computational effort on the slow components.

Multirate methods address this by allowing different components to advance with different step sizes, matched to their respective time scales. This post covers three frameworks — MIS, MRGARK, and the MREEF scheme I implemented in PR #3139 — with the mathematical theory, algorithmic details, and implementation challenges.

1. The Multirate Problem

Consider a partitioned ODE:

$$\frac{dy}{dt} = f^{\{s\}}(t, y) + f^{\{f\}}(t, y)$$

where \(f^{\{s\}}\) is the slow component (varying on time scale \(H\)) and \(f^{\{f\}}\) is the fast component (varying on time scale \(h \ll H\)). The multirate ratio \(M = H/h\) quantifies the scale separation.

A naïve single-rate method must use step size \(h\) everywhere, evaluating the slow component \(M\) times more often than necessary. A multirate method uses step size \(H\) for the slow component and \(h\) for the fast component, reducing the cost by a factor approaching \(M\) for slow-dominated systems.

2. Multirate Infinitesimal Step (MIS) Methods

MIS methods, introduced by Wensch, Knoth, and Galant (2009) and extended by Knoth and Wensch (2014), treat the fast component using an auxiliary ODE within each slow stage.

For an \(s\)-stage slow method with Butcher tableau \((A^{\{s\}}, b^{\{s\}}, c^{\{s\}})\), the MIS approach defines the fast tendency at slow stage \(i\) as:

$$v'(\tau) = f^{\{f\}}(\tau, v(\tau)) + \sum_{j=1}^{i-1} d_{ij} f^{\{s\}}(T_j, Y_j)$$

where \(v(\tau)\) is evolved from \(\tau = t_n + c^{\{s\}}_{i-1} H\) to \(\tau = t_n + c^{\{s\}}_i H\) using a fast explicit integrator with step size \(h\). The coefficients \(d_{ij}\) are derived from the slow Butcher matrix to ensure order conditions are satisfied.

The key advantage of MIS is that the fast integrator can be any explicit RK method — it sees a standard ODE augmented with a time-varying forcing term derived from the slow stages. This modularity makes MIS methods particularly attractive for implementation in a generic solver framework.

# MIS method pseudocode
function mis_step!(y, H, f_slow, f_fast, slow_tableau, fast_solver, M)
    Y = [copy(y) for _ in 1:s]       # Slow stage values
    F_slow = [similar(y) for _ in 1:s] # Slow tendencies

    for i in 1:s
        # Compute slow tendency at stage i
        f_slow(F_slow[i], Y[i], p, t + c[i]*H)

        # Define the "augmented fast ODE" for this stage
        # v' = f_fast(τ, v) + Σ d[i,j] * F_slow[j]
        forcing = sum(d[i+1,j] * F_slow[j] for j in 1:i)

        augmented_f!(dv, v, p, τ) = begin
            f_fast(dv, v, p, τ)
            @. dv += forcing
        end

        # Integrate from c[i]*H to c[i+1]*H using fast solver
        fast_prob = ODEProblem(augmented_f!, Y[i], 
                              (t + c[i]*H, t + c[i+1]*H))
        Y[i+1] = solve(fast_prob, fast_solver, dt=H/M).u[end]
    end
    copyto!(y, Y[s+1])
end

3. Multirate GARK (MRGARK) Framework

The MRGARK framework by Günther and Sandu (2016) provides a unified theoretical foundation for multirate methods based on the Generalized Additive Runge–Kutta (GARK) framework.

A GARK method for a partitioned system decomposes the Butcher tableau into blocks describing interactions between components:

$$\begin{pmatrix} A^{\{ss\}} & A^{\{sf\}} \\ A^{\{fs\}} & A^{\{ff\}} \end{pmatrix}$$

where \(A^{\{ss\}}\) governs slow-to-slow coupling, \(A^{\{ff\}}\) governs fast-to-fast coupling, and the off-diagonal blocks \(A^{\{sf\}}\), \(A^{\{fs\}}\) describe cross-scale interactions.

The MRGARK framework extends this to multirate settings by allowing the fast component to take \(M\) sub-steps per slow stage. The resulting coefficient structure can be expressed as a large partitioned Butcher tableau with specific sparsity patterns dictated by the multirate ratio.

Key theoretical results from Günther and Sandu (2016):

  • Order conditions: Generic order conditions for multirate GARK methods up to order 4, expressed in terms of the block matrices
  • Internal consistency: Conditions ensuring that each sub-method is internally consistent (e.g., the fast method satisfies standard RK order conditions)
  • Stability: Linear stability analysis showing that MIS methods are a special case of the MRGARK framework

4. Design of High-Order Decoupled Methods

Sarshar, Roberts, and Sandu (2019) further developed the MRGARK framework by designing decoupled multirate methods where the slow and fast components can be solved independently within each stage. This is particularly important for parallel implementation and code modularity.

A decoupled method has \(A^{\{sf\}} = 0\) (no fast-to-slow coupling), meaning the slow stages don't depend on the fast sub-step results within the same stage. This simplifies the implementation significantly and enables the use of existing single-rate solvers as "black box" components.

5. The MREEF Implementation (#3139)

The MREEF (Multirate Explicit-Explicit Forward) scheme I implemented in OrdinaryDiffEq.jl is a multirate method where both the slow and fast components are treated explicitly. The implementation required careful attention to:

# Key implementation challenges:

# 1. Sub-stepping interface
# The fast integrator must accept a "forcing function" from
# the slow stages, which changes at each slow stage boundary.

# 2. Interpolation between slow stages
# The slow tendency is only evaluated at slow stage points.
# Between slow stages, we interpolate (often linearly) to
# provide a continuous forcing for the fast integrator.

# 3. Cache management
# The multirate cache must store:
# - All slow stage values and derivatives
# - The fast integrator's internal state
# - Interpolation coefficients for the slow forcing
# Total memory: O(s_slow * n + s_fast * n) where n = problem size

# 4. Adaptive multirate ratio
# In practice, M should adapt based on local stiffness estimates.
# This requires a mechanism to detect when the fast scale changes.

6. Practical Considerations

When to Use Multirate Methods

  • Large multirate ratio (M > 10): The cost savings justify the overhead of managing two integrators
  • Identifiable scale separation: The system can be cleanly split into fast and slow components
  • Slow-dominated cost: Evaluating \(f^{\{s\}}\) is significantly more expensive than \(f^{\{f\}}\)

When NOT to Use Multirate Methods

  • Small M (< 5): The overhead of managing two integrators outweighs the savings
  • Tightly coupled components: When slow and fast dynamics strongly interact, the splitting error dominates
  • Non-smooth transitions: If the fast/slow classification changes over time, fixed multirate methods struggle

7. Connection to the GSoC Project

The multirate implementation is the most algorithmically complex part of the GSoC project. It requires:

  1. Nested integration: The fast integrator runs inside each slow stage, creating a solver-within-a-solver architecture
  2. Generic fast solver interface: Users should be able to choose any explicit RK method as the fast solver
  3. Tableau-driven design: The slow method's tableau defines the coupling coefficients, connecting back to the generic tableau infrastructure
  4. Zero-allocation fast stepping: The fast sub-steps must be allocation-free despite the nested structure

The implementation will leverage the generic tableau infrastructure developed earlier in the project, demonstrating that the same framework can express both single-rate and multirate methods.
