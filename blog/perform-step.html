How perform_step! Works in OrdinaryDiffEq.jl

📅 May 7, 2026🕐 16 min readOpen Source

perform_step! is the heart of every ODE solver in the SciML ecosystem. It's the function that computes a single time step — the numerical kernel that transforms \(y_n\) into \(y_{n+1}\). Understanding its architecture is essential for anyone contributing new solvers or optimizing existing ones.

This post provides a comprehensive walkthrough of the perform_step! pipeline, from the outer integration loop down to the individual stage evaluations. I'll use the Tsit5 (Tsitouras' 5th-order) method as a running example, since it's the default solver for non-stiff problems and one of the most commonly used methods in the ecosystem.

1. The Big Picture: Integration Loop

When you call solve(prob, Tsit5()), the following chain of events occurs:

# Simplified integration pipeline
solve(prob, alg)
  └─ init(prob, alg)              # Create the integrator
       └─ ODEIntegrator(...)      # Holds all state
  └─ solve!(integrator)           # Run the main loop
       └─ while !isempty(integrator.tstops)
            loopheader!(integrator)     # Adaptivity, dt selection
            perform_step!(integrator, cache)  # ← THE CORE
            loopfooter!(integrator)     # Callbacks, saving, error control
          end

The integrator object is a mutable state container that holds:

  • u — the current solution vector
  • t — the current time
  • dt — the current step size
  • p — problem parameters
  • f — the ODE right-hand side function
  • cache — algorithm-specific pre-allocated storage
  • opts — tolerance settings, adaptive stepping parameters, etc.

2. The Cache System

Every solver algorithm has an associated cache type that pre-allocates all working memory needed during a step. This is the foundation of zero-allocation performance. There are two variants:

# Out-of-place (OOP) cache — for small, immutable problems
struct Tsit5ConstantCache{T, T2} <: OrdinaryDiffEqConstantCache
    c2::T2; c3::T2; c4::T2; c5::T2; c6::T2  # Nodes
    a21::T; a31::T; a32::T                     # Butcher coefficients
    a41::T; a42::T; a43::T
    # ... all coefficients stored as scalars
    # No pre-allocated arrays — stages are immutable return values
end

# In-place (IIP) cache — for large, mutable problems
struct Tsit5Cache{uType, rateType, TabType} <: OrdinaryDiffEqMutableCache
    u::uType; uprev::uType        # Solution arrays
    k1::rateType; k2::rateType    # Stage derivative arrays
    k3::rateType; k4::rateType
    k5::rateType; k6::rateType; k7::rateType
    utilde::uType                  # Error estimation workspace
    atmp::uType                    # Absolute tolerance temp
    tab::TabType                   # Tableau coefficients
end

The cache distinction is crucial for performance:

  • OOP (ConstantCache): Used when u is small (e.g., SVector) or immutable. Each f(u, p, t) call returns a new object. No pre-allocated arrays. The compiler can stack-allocate everything.
  • IIP (MutableCache): Used when u is a large mutable array. All stage vectors are pre-allocated in the cache. f(du, u, p, t) writes into du in-place. This avoids heap allocations in the hot loop.

3. Inside perform_step! — The Tsit5 Example

Tsit5 is a 7-stage, 5th-order method with a 4th-order embedded error estimator (for adaptive step size control) and the FSAL property. The in-place perform_step! looks like this (simplified):

function perform_step!(integrator, cache::Tsit5Cache, repeat_step = false)
    # 1. UNPACK — Extract everything from the integrator and cache
    @unpack t, dt, uprev, u, p, f = integrator
    @unpack k1, k2, k3, k4, k5, k6, k7, utilde, atmp = cache
    @unpack c2, c3, c4, c5, c6,
            a21, a31, a32, a41, a42, a43,
            a51, a52, a53, a54,
            a61, a62, a63, a64, a65,
            a71, a72, a73, a74, a75, a76,
            btilde1, btilde2, btilde3, btilde4,
            btilde5, btilde6, btilde7 = cache.tab

    # 2. FSAL — k1 was already computed at the end of the previous step
    # (or during initialization for the first step)

    # 3. STAGE EVALUATIONS — Compute stages k2 through k7
    # Stage 2: Y2 = u + dt * a21 * k1
    @. u = uprev + dt * a21 * k1
    f(k2, u, p, t + c2 * dt)

    # Stage 3: Y3 = u + dt * (a31*k1 + a32*k2)
    @. u = uprev + dt * (a31 * k1 + a32 * k2)
    f(k3, u, p, t + c3 * dt)

    # Stage 4: Y4 = u + dt * (a41*k1 + a42*k2 + a43*k3)
    @. u = uprev + dt * (a41 * k1 + a42 * k2 + a43 * k3)
    f(k4, u, p, t + c4 * dt)

    # ... Stage 5, 6 similarly ...

    # Stage 7 (FSAL): This will be k1 of the NEXT step
    @. u = uprev + dt * (a71*k1 + a72*k2 + a73*k3 +
                         a74*k4 + a75*k5 + a76*k6)
    f(k7, u, p, t + dt)
    # u now holds y_{n+1} (the a7i coefficients = bi weights for Tsit5)

    # 4. ERROR ESTIMATION — Difference between 5th and 4th order solutions
    @. utilde = dt * (btilde1*k1 + btilde2*k2 + btilde3*k3 +
                      btilde4*k4 + btilde5*k5 + btilde6*k6 +
                      btilde7*k7)

    # 5. PACK — Write results back to the integrator
    integrator.EEst = integrator.opts.internalnorm(utilde, t)
    # k7 becomes k1 of the next step (FSAL)
    integrator.fsallast = k7
end

4. The FSAL Optimization

FSAL (First Same As Last) is a critical optimization used by many modern RK methods. The idea: the last stage derivative \(k_s\) of step \(n\) is exactly the first stage derivative \(k_1\) of step \(n+1\), because both are evaluated at the same point \((t_{n+1}, y_{n+1})\).

This saves one function evaluation per step — for Tsit5, that means 6 evaluations per step instead of 7 (a ~14% reduction in the dominant cost). The cache manages this by storing \(k_s\) in the fsallast field and copying it to \(k_1\) at the start of the next step.

5. Adaptive Step Size Control

After perform_step! computes both the solution \(y_{n+1}\) and the error estimate, the loopfooter! function uses the error estimate to decide whether to accept or reject the step and how to adjust \(dt\).

The error is typically controlled using the formula:

$$\text{EEst} = \left\| \frac{y_{n+1}^{(p)} - y_{n+1}^{(p-1)}}{\text{abstol} + \text{reltol} \cdot |y_{n+1}|} \right\|$$

If EEst ≤ 1, the step is accepted. If EEst > 1, the step is rejected and retried with a smaller \(dt\). The new step size is computed using the PI controller:

$$dt_{\text{new}} = dt \cdot \min\left(q_{\max}, \max\left(q_{\min}, q \cdot \text{EEst}^{-1/(p+1)}\right)\right)$$

where \(q\) is a safety factor (typically 0.9) and \(p\) is the method order.

6. The Dispatch Mechanism

Julia's multiple dispatch is what makes the entire architecture possible. When you call solve(prob, Tsit5()):

  1. The alg_cache function dispatches on the algorithm type to create the appropriate cache
  2. The perform_step! function dispatches on the cache type to run the correct numerical method
  3. The compiler specializes the entire call chain for the specific types, eliminating all dynamic dispatch overhead
# The dispatch chain
alg_cache(alg::Tsit5, u, ...) → Tsit5Cache(...)
perform_step!(integrator, cache::Tsit5Cache) → specialized code

# At compile time, Julia generates optimized machine code
# specifically for Tsit5Cache, with all coefficient accesses
# resolved to constants and all loops unrolled.

7. Why This Matters for the Refactoring

Understanding the perform_step! pipeline reveals exactly what the generic tableau architecture must replicate:

  • The cache must pre-allocate the correct number of stage vectors (determined by the tableau)
  • The stage loop must handle both FSAL and non-FSAL methods
  • The error estimation must use the embedded coefficients from the tableau
  • The type parametrization must enable the same level of compiler specialization

The generic version doesn't change what perform_step! does — it changes how many times it's written. Instead of N separate implementations for N methods, we have one implementation parametrized by a tableau.
