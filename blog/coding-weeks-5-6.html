GSoC 2026 Weeks 5–6 — Closing the Explicit Multirate Ladder & Hardening NonlinearSolveAlg

June 27, 20267 min readGSoC

The last cycle closed with two explicit MRI-GARK methods still open for review. This fortnight finished that ladder, picked up an order-10 tableau as a side quest, and — more consequentially — started tearing into NonlinearSolveAlg's cache and W-reuse machinery, which turned out to be the real prerequisite for the implicit multirate solvers coming next.

Completing the explicit MRI-GARK family

The two PRs left in flight from last cycle both landed, taking the family from order 2 to order 4 on one unified formulation.

  • #3747: Added MRI-GARK-ERK33a (order 3, Sandu 2019) and re-expressed ERK22a/ERK22b onto the same formulation — one perform_step! now handles the whole family via per-stage sub-interval integration with τ-dependent coupling ω = W0 + W1·τ.
  • #3751: Added the 4th-order explicit MRI-GARK-ERK45a, closing the explicit order ladder at 2 → 3 → 4.

A side quest: MSRK10

Between multirate PRs I picked up a standing issue from the tableau backlog:

  • #3755: Added MSRK10, Misha Stepanov's explicit 15-stage order-10 Runge-Kutta method (arXiv:2504.17329), as an ExplicitRK tableau alongside Ono10, Curtis10, and Feagin10. The embedded order-8 estimator makes it a (10,8) adaptive pair, and a BigFloat convergence test mirrors the existing order-10 coverage.

Small in scope, but useful as a reset between the heavier multirate and nonlinear-solve work.

Hardening NonlinearSolveAlg

The implicit MRI-GARK methods planned for next cycle solve a nonlinear system at every slow stage via NonlinearSolveAlg. Before adding them, several latent bugs in that path needed fixing — problems that explicit multirate and the existing SDIRK/FBDF steppers never exercised because they don't resize or reuse the nonlinear cache the way a solve-decoupled implicit multirate stepper does.

  • #3753: Extended W-reuse to WOperators built around a concrete Jacobian — the common setup when a user picks an iterative linsolve like KrylovJL_GMRES with concrete_jac = true. Previously build_nlsolver gated use_w_reuse on W isa AbstractMatrix && !(W isa AbstractSciMLOperator), which excluded WOperator outright even though its _concrete_form field already carries the materialized M/γdt - J.
  • #3797: Hoisted a dead linprob/linsolve allocation out of the hot path in the NLNewton branch.
  • #3794: Dropped a duplicate nnonliniter accumulation and guarded a resize firstcall write that was overwriting state it shouldn't touch.
  • #3799: Defined Base.resize! for NonlinearSolveCache and guarded the firstcall write. resize!(integrator, N) on an integrator using NonlinearSolveAlg was breaking two different ways: the resize call fell through to an undefined default, and resize_nlsolver! was unconditionally setting a firstcall field that NonlinearSolveCache doesn't even have.
Why this mattered more than it looked

None of these bugs were visible from the outside — SDIRK and FBDF never resize the nonlinear cache mid-solve, so NonlinearSolveCache's missing resize! and phantom firstcall field had simply never been exercised. Solve-decoupled implicit multirate methods resize constantly as the fast/slow step sizes adapt independently, so every one of these had to be fixed before #3811 could even run.

Closing out the cycle

The last few days of the fortnight rounded out test coverage and CI hygiene for the changes above:

  • #3804: Extended ode_cache_tests to cover KenCarp4 and ImplicitEuler with NonlinearSolveAlg.
  • #3805: Added u/uprev fields to QNDFCache so resize! propagates correctly to integrator.u/uprev — a related resize gap found while chasing the NonlinearSolveAlg bugs.
  • #3808: Raised the downgrade-CI compat floors for TruncatedStacktraces and RecursiveArrayTools after the resize changes needed newer minimum versions.
  • #3757: Documented EulerHeun as the two-stage Stratonovich Heun method.
  • #3758: Fixed pre-existing runic formatting failures in callbacks.jl and the multi-VCC mask tests.

Challenges this cycle

  • Invisible bugs: the NonlinearSolveAlg resize/W-reuse issues had no test coverage anywhere in the package because nothing previously exercised that code path — finding them meant reasoning from the implicit multirate design forward rather than from a failing test backward.
  • Sequencing: landing the cache hardening before the implicit solvers themselves meant a fortnight with no new user-facing multirate method, even though it was the necessary foundation for two of them.

Goals for the next two weeks

  • Land the first implicit MRI-GARK method, MRIGARKIRK21a, now that the nonlinear-solve cache is solid.
  • Follow with a stiff-slow-subsystem variant, MRIGARKESDIRK34a, building on the same solve-decoupled machinery.
  • Keep chasing W-operator/mass-matrix plumbing gaps surfaced by the implicit path.
  • Fill in remaining SDIRK backlog items opportunistically between multirate PRs.

Closing thoughts

This fortnight had less to show in terms of new methods than the last one, but it's the kind of work that determines whether the next fortnight goes smoothly. Finding and fixing four separate NonlinearSolveAlg bugs before they could block the implicit multirate solvers was slower than just writing MRIGARKIRK21a and hitting the errors one at a time — but cheaper in the end. Onward to implicit multirate.
