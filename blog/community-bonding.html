About the Project

My project is titled "Native Julia ODE, SDE, DAE, DDE, and PDE Solvers".

Currently, OrdinaryDiffEq.jl — one of the most comprehensive ODE solver libraries — suffers from code duplication. Most solver families have their own bespoke perform_step! implementation. For instance, the logic is identical across KenCarp3, KenCarp4, KenCarp5, and the rest of the IMEX family; only the coefficient tables differ. That's roughly ~3,300 lines of duplicated stepping code!

Why this matters

Every solver family that adopts the generic tableau eliminates an entire bespoke perform_step! — one bug fix now lands across all of them at once, and adding a new IMEX method becomes a tableau-only change.

This project introduces a generic IMEXTableau{Texplicit, Timplicit} struct that holds the Butcher arrays for any IMEX method, backed by a single shared perform_step! function. We will also extend this generic tableau refactor to all 16 RK-based solver families. This transition ensures easier maintenance, fewer bugs, consistent zero-allocation optimizations, and dramatically easier integration of future numerical methods. We'll additionally build robust multirate methods (MREIL, MIS, MRGARK) to optimize systems where components evolve at vastly different timescales.

Community Bonding Activities

The community bonding period is all about aligning with the community, setting up the development environment, and preparing for the coding phase. I've had a highly productive Week 0:

  • Discussions with Mentors: I synced up with Chris Rackauckas regarding expectations for the midterm evaluation. We agreed that by Week 6, the IMEXTableau should be fully stable and merged (ARS/ESDIRK + another method like Pareschi–Russo), alongside the initial RK migration (like LowStorageRK).
  • Reviewing Previous PRs/Issues: I've been actively following the discussions surrounding the generic tableau architectures and resolving immediate bugs and behavioral regressions from my early groundwork.
  • Running Tests & Benchmarks: I spent significant time testing the new abstractions against existing benchmarks to ensure strict zero-allocation performance and correctness.

Technical Learnings & Contributions

Rather than just reading documentation, I spent my bonding period actively shipping code to stabilize the abstractions I proposed. Over the past couple of weeks, several major architectural PRs were merged into OrdinaryDiffEq.jl. Most of this work focused on reducing duplication while preserving numerical correctness and zero-allocation performance guarantees.

  • #3196: Introduced the generic IMEX tableau abstraction with shared perform_step! for ARS/ESDIRK methods.
  • #3641: Fixed crucial behavioral regressions in the generic SDIRK/IMEX stepping kernels.
  • #3621: Unified SFSDIRK4-8 and Hairer4/42 into a robust generic PureSDIRK implementation.
  • #3590: Refactored LowStorageRK, unifying alg_cache and resolving unbound type parameter issues.
  • #3591: Specialized the tableau, extras, and interpolation constructors for Verner solvers.
  • #3597: Tightened the Kvaerno3 + NLFunctional convergence test to fix algebraic solver issues.
  • #3624: Fixed an ARS343 BoundsError by adjusting split_guess indices.

What I've Learned So Far

This initial refactoring phase has been highly educational. I've learned first-hand how numerical behavior changes under generic abstractions and the critical importance of preserving solver invariants. I also realized just how sensitive CI convergence tests are in scientific computing. Balancing clean architectural abstraction with the strict performance demands of a zero-allocation numerical kernel requires meticulous attention to detail.

Challenges Faced

Refactoring the core stepper of an ecosystem as vast as SciML comes with intricate challenges:

  • Behavioral Regressions: While unifying SDIRK/IMEX, maintaining identical numerical behavior to the old bespoke methods took intense debugging, as seen in PR #3641.
  • Convergence Test Sensitivities: Trivial changes in generic dispatch occasionally trigger failures in highly sensitive convergence tests (e.g., Kvaerno3 + NLFunctional), forcing me to deeply investigate tolerance levels and algebraic solver interplay.
  • Type Stability & Bounds: Unifying caches meant tracking down tricky unbound type parameters and resolving BoundsError bugs when generic arrays interact with specific solver assumptions.

Goals for the Upcoming Weeks

As we transition into the official coding phase, my main goals are:

  • Finalize and harden the IMEXTableau abstraction (ensuring zero-allocations and speed parity).
  • Introduce the Pareschi–Russo IMEX-ARK method as the next robust test for the generic framework.
  • Aggressively migrate the LowStorageRK solver family.
  • Ensure all migrated solvers seamlessly pass the strict convergence and regression suites.
  • Begin architectural planning for the linearly implicit multirate solver (MREIL).
