Understanding IMEX Runge–Kutta Methods

📅 May 7, 2026🕐 14 min readNumerical Methods

Many real-world systems have both stiff and non-stiff parts. Think of climate models coupling fast acoustic waves with slow advection, or chemical reactions mixing rapid changes with slow transport. Treating everything implicitly is too slow, but treating everything explicitly blows up. IMEX (Implicit-Explicit) Runge–Kutta methods fix this by splitting the math and applying the right tool to each piece.

This post breaks down IMEX-RK methods — how the math works, how we code them, and why they matter for OrdinaryDiffEq.jl. This directly drives the generic tableau architecture I'm building for GSoC 2026.

1. The Splitting Problem

Consider an ODE of the form:

$$\frac{dy}{dt} = f(t, y) + g(t, y)$$

where \(f\) represents the non-stiff component (e.g., advection, hyperbolic terms) and \(g\) represents the stiff component (e.g., diffusion, fast chemical reactions). The idea is simple:

  • Apply an explicit RK method to \(f\) — no linear solves needed, cheap per stage
  • Apply an implicit RK method to \(g\) — unconditionally stable for stiff terms

This approach was really pushed forward by Ascher, Ruuth, and Spiteri (1997) for convection-diffusion PDEs. They figured out that partitioned Runge–Kutta schemes could beat the nasty time-step limits of older IMEX methods while still being easy to start up.

2. Double Butcher Tableau

An \(s\)-stage IMEX-RK method is defined by a pair of Butcher tableaus — one for the explicit part, one for the implicit:

Explicit tableau \((\tilde{A}, \tilde{b}, \tilde{c})\):

$$\begin{array}{c|c} \tilde{c} & \tilde{A} \\ \hline & \tilde{b}^T \end{array}$$

where \(\tilde{A}\) is strictly lower triangular (no implicit coupling between stages).

Implicit tableau \((A, b, c)\):

$$\begin{array}{c|c} c & A \\ \hline & b^T \end{array}$$

where \(A\) is lower triangular (diagonally implicit — DIRK structure), meaning each implicit stage can be solved independently.

The combined IMEX method computes stage values as:

$$Y_i = y_n + h \sum_{j=1}^{i-1} \tilde{a}_{ij} f(t_n + \tilde{c}_j h, Y_j) + h \sum_{j=1}^{i} a_{ij} g(t_n + c_j h, Y_j)$$

$$y_{n+1} = y_n + h \sum_{i=1}^{s} \tilde{b}_i f(t_n + \tilde{c}_i h, Y_i) + h \sum_{i=1}^{s} b_i g(t_n + c_i h, Y_i)$$

The critical structural requirement is that at each stage \(i\), the explicit part uses only previous stages (\(j < i\)), while the implicit part may use the current stage (\(j = i\)). This allows a sequential solve: at each stage, we solve a (generally nonlinear) equation for \(Y_i\) involving only known quantities and the implicit diagonal coefficient \(a_{ii}\).

3. SDIRK Structure and Efficient Solves

A particularly important subclass uses SDIRK (Singly Diagonally Implicit RK) structure for the implicit tableau, where all diagonal entries are equal: \(a_{ii} = \gamma\) for all \(i\). This is critical for efficiency because:

  • The Jacobian matrix \(I - h\gamma J_g\) is the same at every stage
  • A single LU factorization can be reused across all implicit stage solves within one step
  • For large systems (e.g., semi-discretized PDEs), this reduces the cost from \(O(s \cdot n^3)\) to \(O(n^3 + s \cdot n^2)\)

Kennedy and Carpenter (2003) built several high-order ARK (Additive Runge–Kutta) methods with this SDIRK property, like the popular ARK4(3)6L[2]SA scheme — a fourth-order, six-stage method. You'll find these in heavy-duty production codes like PETSc's TSARKIMEX.

4. Order Conditions

The order conditions for IMEX-RK methods are more complex than for standalone RK methods. For an IMEX pair to achieve order \(p\), both the explicit and implicit tableaus must individually satisfy order-\(p\) conditions, and a set of coupling conditions must hold between the two tableaus.

For order 1: \(\sum_i b_i = 1\) and \(\sum_i \tilde{b}_i = 1\)

For order 2, in addition: \(\sum_i b_i c_i = \frac{1}{2}\), \(\sum_i \tilde{b}_i \tilde{c}_i = \frac{1}{2}\), and coupling conditions like \(\sum_i b_i \tilde{c}_i = \frac{1}{2}\) and \(\sum_i \tilde{b}_i c_i = \frac{1}{2}\).

At higher orders, the number of coupling conditions grows rapidly. Butcher's rooted tree theory extends to pairs of trees (one for each component), and each tree generates an algebraic condition on the combined tableau coefficients. This complexity is one reason why relatively few high-order IMEX-RK methods exist in the literature.

5. Stability Analysis

The stability of an IMEX method is analyzed by applying it to the test equation:

$$y' = \lambda_f y + \lambda_g y$$

where \(\lambda_f\) (explicit, non-stiff part) lies near the imaginary axis and \(\lambda_g\) (implicit, stiff part) lies in the left half-plane. The stability function becomes a rational function of two variables, \(R(z_f, z_g)\), where \(z_f = h\lambda_f\) and \(z_g = h\lambda_g\).

A well-designed IMEX method should be:

  • A-stable in the implicit variable (stable for all \(z_g\) with \(\text{Re}(z_g) \leq 0\))
  • Have a large stability region along the imaginary axis in the explicit variable
  • Be L-stable if possible (amplification factor \(\to 0\) as \(z_g \to -\infty\)), which damps fast transients

6. Implementation in Julia

In OrdinaryDiffEq.jl, the current architecture defines each IMEX method with its own dedicated perform_step! function. Here's a simplified view of what this looks like:

# Current approach: separate perform_step! per method
function perform_step!(integrator, cache::KenCarp4Cache, repeat_step=false)
    @unpack t, dt, u, p = integrator
    @unpack k1, k2, k3, k4, k5, k6 = cache
    @unpack a21, a31, a32, ... = cache.tab   # Hardcoded coefficients

    # Stage 1
    f.f1(k1, u, p, t)                        # Explicit evaluation
    # Stage 2
    tmp = u + dt * a21 * k1
    # Implicit solve for k2...
    # ... (repeated for each stage)
end

The generic IMEXTableau approach I'm building replaces this with:

# Generic approach: one perform_step! for all IMEX methods
struct IMEXTableau{sType, T}
    A_exp::SMatrix{sType, sType, T}    # Explicit Butcher matrix
    A_imp::SMatrix{sType, sType, T}    # Implicit Butcher matrix (DIRK)
    b_exp::SVector{sType, T}           # Explicit weights
    b_imp::SVector{sType, T}           # Implicit weights
    c_exp::SVector{sType, T}           # Explicit nodes
    c_imp::SVector{sType, T}           # Implicit nodes
end

function perform_step!(integrator, cache::GenericIMEXCache, repeat_step=false)
    @unpack tab = cache
    s = nstages(tab)

    for i in 1:s
        # Accumulate explicit contributions from previous stages
        @. tmp = u
        for j in 1:i-1
            @. tmp += dt * tab.A_exp[i,j] * K_exp[j]
            @. tmp += dt * tab.A_imp[i,j] * K_imp[j]
        end
        # Implicit solve for stage i
        solve_implicit_stage!(K_imp[i], tmp, dt * tab.A_imp[i,i], ...)
        # Explicit evaluation at stage i
        f.f1(K_exp[i], Y[i], p, t + tab.c_exp[i] * dt)
    end
    # Update solution
    @. u = u_prev
    for i in 1:s
        @. u += dt * tab.b_exp[i] * K_exp[i]
        @. u += dt * tab.b_imp[i] * K_imp[i]
    end
end

The advantage is clear: one implementation serves all IMEX methods. Adding a new IMEX scheme reduces to defining its tableau coefficients — no new perform_step! code required.

7. The Challenge: Performance Parity

The generic approach introduces a tension: generality vs. performance. Hand-written kernels can be tuned for specific stage counts and exploit FSAL (First Same As Last) properties. The generic version must:

  • Avoid heap allocations in the inner loop — achieved via pre-allocated caches and @views
  • Enable compiler optimization — using @inbounds and @simd where safe, and ensuring type stability via parametric tableau types
  • Match loop unrolling — when the stage count is known at compile time (via type parameters), Julia's compiler can unroll the stage loops, recovering the performance of hand-written code

Our benchmarks on the Van der Pol equation (stiffness parameter \(\mu = 10^6\)) and the HIRES chemical reaction network show that the generic implementation achieves within 2% of the handwritten kernel performance when the tableau is type-parametrized.
