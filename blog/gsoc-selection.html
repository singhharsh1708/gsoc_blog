Getting Selected for GSoC 2026 with SciML

📅 May 7, 2026🕐 10 min readGSoC

I'm thrilled to share that I've been selected as a Google Summer of Code 2026 contributor under SciML (NumFOCUS). My project — "Native Julia ODE, SDE, DAE, DDE, and PDE Solvers" — focuses on refactoring the core stepping infrastructure of OrdinaryDiffEq.jl, focusing on zero-allocation performance and generic dispatch.

This post is a detailed account of how I got here — from starting my first contributions in January 2026 to rapidly learning numerical software development, and ultimately prototyping a major solver refactor that became my GSoC proposal.

Why SciML and Julia?

My interest in numerical computing started during my second year of undergraduate studies. I was fascinated by how differential equations underpin everything from weather prediction to molecular dynamics. When I discovered Julia — a language designed from the ground up for scientific computing — and the SciML ecosystem built on top of it, I knew I'd found my niche.

The SciML ecosystem, led by Chris Rackauckas and others, is remarkable in scope. As described in the foundational paper "DifferentialEquations.jl – A Performant and Feature-Rich Ecosystem for Solving Differential Equations in Julia" (Rackauckas & Nie, 2017, Journal of Open Research Software), the ecosystem provides a unified interface for ODEs, SDEs, DDEs, DAEs, and more — all while matching or exceeding the performance of established Fortran/C libraries like Sundials and LSODA.

What drew me in wasn't just using the tools, but understanding how they work under the hood. I wanted to learn by doing, diving straight into the code and learning numerical solver design through active implementation.

The Contribution Journey

Starting with Benchmarks and Validation (Jan-Mar)

I started my SciML journey around January 2026, focusing heavily on SciMLBenchmarks.jl. Before writing solvers, I needed to understand how to validate them. Over a two-month period until mid-March, I contributed 8 DAE benchmarks covering Index-1 through Index-3 problems from mechanical and electrical engineering.

This phase was critical. Working with work-precision diagrams and validation suites taught me what performance in numerical computing actually means. It forced me to understand solver internals by seeing how different algorithms performed under stress.

Phase 1: Moving to Solvers — Ralston4 (#3215)

My first contribution was implementing the Ralston4 solver pipeline. Ralston's fourth-order method is a classical explicit Runge–Kutta scheme that minimizes the leading truncation error coefficient. It's defined by a specific Butcher tableau:

# Ralston4 Butcher Tableau
# c | A
# --|----
#   | b^T
#
# 0   |  0
# 0.4 |  0.4
# 0.4557 | 0.29698 0.15875
# 1   | 0.21827 -3.05097 3.83274 0
# ----|----------------------------
#     | 0.17476 -0.55149 1.20553 0.17118

While simple mathematically, this PR taught me the entire SciML solver development workflow:

  • Algorithm struct definition: Defining the type that users dispatch on (e.g., Ralston4())
  • Cache construction: Setting up pre-allocated work arrays for zero-allocation stepping
  • perform_step! implementation: The core numerical kernel — both in-place (IIP) and out-of-place (OOP) variants
  • Interpolation: Dense output for continuous solution representation between time steps
  • Testing and CI: Running the full SciML test suite and ensuring convergence order

Phase 2: Scaling Up and Performance — LSRK Methods (#3241)

After Ralston4, I took on a much larger task: implementing 16 energy-stable, discontinuous-Galerkin-optimized low-storage Runge–Kutta (LSRK) methods. This was my crash course in high-performance computing in Julia.

Low-storage methods require intense focus on memory allocation. I had to ensure type stability, optimize cache structures, and guarantee zero-allocation kernels. Learning to squeeze maximum performance out of Julia was a steep but incredibly rewarding learning curve.

Phase 3: Advanced Solvers — pRRK and IMEX (#3246, #3196)

I then implemented positivity-preserving relaxation Runge–Kutta (pRRK) methods — schemes that guarantee the numerical solution preserves physical constraints like positivity of density or concentration. This required understanding relaxation parameters and their role in modifying the step to maintain invariants.

The IMEXTableau framework (#3196) was my most architecturally significant contribution. Instead of hand-coding each IMEX solver separately, I designed a generic tableau type that could be parametrized by coefficients, enabling a single perform_step! implementation to serve multiple IMEX schemes.

Phase 4: The Generic Infrastructure Prototype

Working through these implementations within a rapid ~10 day period leading up to GSoC, a pattern emerged: we were writing the same code over and over.

The Proposal: Refactoring 3,300 Lines of Duplicated Code

The core insight behind my proposal came from a pattern I noticed while implementing solvers: OrdinaryDiffEq.jl contained approximately 3,300 lines of duplicated perform_step! implementations across Runge–Kutta and IMEX solver families. Each solver essentially implemented the same mathematical structure with different tableau coefficients.

The key idea: replace hand-written stepping code with generic, tableau-driven dispatch — fewer lines of code, the same performance, and dramatically easier maintenance.

The proposal covers four major workstreams:

  1. IMEXTableau stabilization — Finalizing the generic type, dispatch infrastructure, and order condition verification using the framework from Kennedy & Carpenter (2003)
  2. RK family migration — Migrating existing ERK, DIRK, and IMEX solvers to the new generic infrastructure
  3. Multirate methods — Implementing MREIL, MIS (Knoth & Wensch, 2014), and MRGARK (Günther & Sandu, 2016) schemes for multi-scale problems
  4. Benchmarking — Ensuring zero-allocation, performance-parity with the existing handwritten kernels

What Made the Proposal Stand Out

Looking back, I think several factors contributed to a successful proposal:

  • Rapid execution: Showing I could learn fast, moving from benchmarks to core solver implementations quickly
  • Specificity: The proposal cited exact line counts, specific files, and concrete performance targets — not vague promises
  • Progressive complexity: My contribution history showed growth from simple solvers to complex infrastructure
  • Alignment with maintainer priorities: The refactoring directly addressed technical debt that Chris and other maintainers had identified
  • Feasibility: The IMEXTableau framework (#3196) was already partially implemented, proving the concept worked

Advice for Future Applicants

  1. Start early, but focus on rapid learning. I started in January and spent the first few months heavily on benchmarks before accelerating into core solvers.
  2. Learn by implementing. Don't just read the code—break it, write a simple solver, and see how the tests respond. The best way to understand an architecture is to build within it.
  3. Communicate with mentors. I was active in the SciML Slack/Zulip channels, asked questions, and shared ideas. Mentors remember contributors who are engaged.
  4. Show progressive complexity. Start simple and escalate. Reviewers notice growth from "implemented a basic RK method" to "designed a generic tableau infrastructure."
  5. Write a specific proposal. Generic proposals get rejected. Know the code, cite line numbers, and show you've done the work.
  6. Choose a project you genuinely care about. The passion shows in both the proposal and the contributions.
