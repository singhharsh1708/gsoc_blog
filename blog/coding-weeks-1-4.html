GSoC 2026 Weeks 1–4 — New IMEX Schemes & the First Multirate Solvers

June 13, 20268 min readGSoC

The coding phase is in full swing. Over the last few weeks the generic IMEXTableau stopped being scaffolding and started paying for itself — I finalized the SDIRK/IMEX migration, then used the new abstraction to ship a whole family of real IMEX-RK methods and the first batch of multirate solvers into OrdinaryDiffEq.jl.

Where things stand

In the Week 0 post I described the plan: collapse the per-family perform_step! kernels into a single generic dispatch driven by a tableau, then use that foundation to add new methods cheaply. The work since then splits into three arcs — hardening the tableau, shipping IMEX-RK methods on top of it, and standing up multirate integration. Most of this is now merged into master.

The payoff of the refactor

Once the generic stepper was solid, adding ARS222, ARS232, ARS443, the IMEX-SSP family, and BHR(5,5,3) became tableau-only changes — no new perform_step!, no new cache, no new bug surface. That is exactly the leverage the refactor was supposed to buy.

Arc 1 — Finalizing the SDIRK/IMEX tableau

The first job was making the generic stepper behave identically to the bespoke kernels it replaces, across every edge case, before I trusted it with new methods.

  • #3650: Unified error estimation under a single dispatched calculate_error_estimate!, so embedded-pair error control lives in one place instead of being re-derived per family.
  • #3651: Migrated CFNLIRK3 into the ESDIRKIMEX tableau form.
  • #3654: Forced type specialization of the ESDIRK*L2SA tableau dispatches to keep them zero-allocation and type-stable.
  • #3656: Migrated the ABDF2 Euler cache onto ESDIRKIMEXCache and dropped the legacy implicit-Euler caches.
  • #3661: Added a tableau embedded-pair consistency test for adaptive SDIRK/ESDIRK methods — a guardrail so future tableau edits can't silently break adaptivity.
  • #3662: Fixed the ESDIRK659L2SA embedded coefficients so adaptive solves actually work (#3659).
  • #3668: Added a generic stage-predictor menu for ESDIRK methods, so initial guesses for the implicit stages can be chosen consistently across the family.
  • #3670: Fixed linsolve propagation through the nonlinear-solver algorithm so the configured linear solver actually reaches the inner Newton solve.

Reusing the W matrix as a Jacobian

A nice side quest here was teaching the nonlinear solver to reuse work the ODE integrator has already done. The implicit RK stages factor a W = I - γΔt·J matrix every step; the embedded nonlinear solve was recomputing Jacobian information it could have borrowed.

  • #3693: Made NonlinearSolveAlg reuse the ODE solver's W matrix as an analytic Jacobian (#2757).
  • #3703: Extended the modified-Newton path to the nlstep/DAE/out-of-place code paths (#3696).

Arc 2 — Real IMEX-RK methods on the generic stepper

With the foundation stable, this is where the refactor started returning dividends. Each of these methods is just a pair of Butcher tableaus handed to the shared kernel — implicit-explicit schemes that are workhorses for convection–diffusion–reaction problems where the stiff part is treated implicitly and the rest explicitly.

  • #3704: Added the ARS222, ARS232, and ARS443 IMEX-RK schemes (Ascher–Ruuth–Spiteri).
  • #3705: Added the IMEX-SSP family and extended ESDIRKIMEXTableau to support non-ESDIRK structures.
  • #3706: Added the BHR(5,5,3) IMEX-RK method (Boscarino–Russo 2009).

Arc 3 — The first multirate solvers

The multirate deliverable is the part I'm most excited about. Multirate methods exploit the fact that in many systems some components evolve far faster than others — instead of forcing the whole system onto the smallest stable step, you integrate the fast and slow partitions with different step sizes and couple them carefully. Over these weeks the first solvers landed:

  • #3707: Added the MRAB (multirate Adams–Bashforth, k-step) explicit solver.
  • #3717: Added MIS2 (Wensch–Knoth–Galant 2009) and refactored the multirate tableau/file structure so subsequent methods slot in cleanly.
  • #3724: Added the MRI-GARK-ERK22a and ERK22b methods (Sandu 2019) — my entry into the Multirate Infinitesimal GARK framework.
  • #3741: Fused the MRI-GARK slow-forcing accumulation to cut redundant work in the coupling step (follow-up to #3724).

And there's a queue of MRI-GARK work in flight as I write this:

  • #3747 (open): Adds the 3rd-order MRI-GARK-ERK33a and unifies the MRI-GARK formulation so all orders share one path.
  • #3751 (open): Adds the 4th-order explicit MRI-GARK-ERK45a.
  • MTK #4609 (open): A cross-repo fix in ModelingToolkit.jl — forwarding the outer ODEFunction's flag down to the inner nonlinear problem in ODENLStepData.

Challenges this cycle

  • Getting MRI-GARK coupling right: the Multirate Infinitesimal framework expresses the slow dynamics as a forcing function on an inner "fast" ODE that's integrated over each slow stage. Translating Sandu's coupling coefficients into an allocation-free stepper — and getting the slow-forcing accumulation to match the reference order numerically — was the hardest debugging of the cycle.
  • Tolerance archaeology: a recurring theme. The autonomous Robertson convergence test needed its tolerance loosened (#3716) once the nlstep path changed, and several IMEX additions surfaced convergence tests that were quietly over-tight.
  • Non-ESDIRK structures in an ESDIRK-shaped tableau: the IMEX-SSP methods don't have the explicit-first-stage assumption baked into the original tableau, which forced #3705 to generalize the abstraction without regressing the ESDIRK fast path.

Goals for the next two weeks

Heading toward the midterm checkpoint, the priorities are:

  • Land #3747 and #3751 to complete the explicit MRI-GARK order ladder (2nd → 4th).
  • Start the LowStorageRK migration in earnest — the 2N-form scaffold (#3683) is open and needs the 2C/3S*/3S*+ variants built out on top.
  • Push toward an implicit/IMEX MRI-GARK variant now that the explicit framework is unified.
  • Keep the convergence and zero-allocation suites green across everything that's been added.

Closing thoughts

This is the stretch where the architecture stopped being a promise and started being a tool. The clearest signal is the velocity: once the generic stepper was trustworthy, adding a vetted IMEX scheme went from "write and debug a new kernel" to "write down a tableau and a test." Multirate is the genuinely new ground, and getting the first MRI-GARK methods to match their reference orders has been the most satisfying part of GSoC so far. Onward to the midterm.
