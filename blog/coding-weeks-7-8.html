GSoC 2026 Weeks 7–8 — The First Implicit Multirate Solvers

July 12, 20268 min readGSoC

The NonlinearSolveAlg hardening from last cycle paid off immediately: this fortnight landed the first two implicit MRI-GARK solvers, plus a run of mass-matrix and WOperator plumbing fixes the implicit path exposed, a new SDIRK scheme, and a correctness fix in the extrapolation family.

The first implicit multirate solvers

Explicit MRI-GARK methods can't handle a stiff slow subsystem — the whole point of going implicit. Solve-decoupled implicit multirate methods solve a nonlinear system for the slow stage value, then integrate the fast component as a forced sub-problem, without coupling the two solves together.

  • #3811: Added MRIGARKIRK21a (Sandu 2019), the first implicit member of the family — order 2, solving SplitODEProblems du/dt = f1(u,t) + f2(u,t) (fast/slow, SciML convention) with the slow stages coupled implicitly to f2 at the stage endpoint.
  • #3812: Added MRIGARKESDIRK34a, order 3, a 6-stage method built directly on the solve-decoupled machinery from #3811 — and, critically, stable when the slow subsystem is itself stiff, which no explicit MRI-GARK method in the package can handle.
Where the Weeks 5–6 work paid off

#3811 is the exact code path that #3799's NonlinearSolveCache resize fix and #3753's WOperator W-reuse extension exist for. Writing the stepper itself took less time than the prep work — the payoff of fixing the foundation first instead of debugging both layers at once.

Mass-matrix and WOperator plumbing

Running the implicit solvers against DAE-flavored and operator-based problems surfaced a cluster of related gaps in how the package handles non-Matrix mass matrices and Jacobians:

  • #3796: Made the out-of-place NLNewton path handle an AbstractSciMLOperator W via update_coefficients! + materialize, instead of erroring outright.
  • #3824: Fixed OOP build_J_W for a MatrixOperator mass matrix — the fallback path built W via lu_instance(J - f.mass_matrix * inv(dtgamma)), which for a MatrixOperator produces an AddedOperator with no lu_instance method, erroring at cache construction.
  • #3795: Piped wrapprecs into the inner algorithm in NonlinearSolveAlg and updated the preconditioner weight per step, instead of leaving it stale after the first solve.
  • #3837: Fixed get_differential_vars to accept IdentityOperator and ScalarOperator mass matrices — a follow-up to #3814 that hit MethodError: no method matching iterate(::IdentityOperator) because the function tried to iterate the operator directly instead of treating it like UniformScaling.
A pattern, not four bugs

#3796, #3824, and #3837 are the same root cause wearing three different masks: code that assumes W or the mass matrix is a concrete Matrix and falls over when it's an AbstractSciMLOperator instead. Each fix is small on its own, but recognizing the pattern across three call sites was what let #3837 get diagnosed in minutes instead of hours.

Elsewhere in the package

  • #3827: Added ESDIRK3(2)5L[2]SA (Kennedy-Carpenter 2019, order 3) — the last remaining scheme from that paper; the other five were already in OrdinaryDiffEqSDIRK.
  • #3756: Fixed the extrapolation error-estimate denominator to use the actual step endpoints max(|uprev|, |u|) instead of max(|u₀|, |u₁|), where u₁ is the lower-order non-stepped extrapolation candidate whose magnitude was incorrectly leaking into step-size control.
  • #3828: Bumped the SciMLBase compat floor from 3.10 to 3.30 across sublibraries, aligning everything on the version the mass-matrix fixes above actually need.

Challenges this cycle

  • Debugging across two solves: a solve-decoupled implicit multirate failure can originate in the slow nonlinear solve, the fast forced sub-integration, or the coupling between them — isolating which one meant instrumenting each independently rather than trusting the first stack trace.
  • Operator-shaped edge cases: the mass-matrix/WOperator bugs only show up for users who pass SciMLOperators types instead of plain matrices, so none of them had test coverage until the implicit multirate path started exercising them directly.

Goals for the next two weeks

  • Push the implicit MRI-GARK order ladder past order 3, mirroring the explicit family's progression.
  • Continue sweeping for remaining AbstractSciMLOperator gaps in the implicit path now that the pattern is known.
  • Write convergence and zero-allocation benchmarks specifically for the solve-decoupled implicit multirate methods.
  • Start drafting the midterm-to-final writeup of the multirate deliverable.

Closing thoughts

Landing MRIGARKIRK21a and MRIGARKESDIRK34a is the deliverable I've been building toward since Weeks 3–4 — explicit multirate was the easier half, and implicit is where the project's actual difficulty lives. The mass-matrix and WOperator fixes weren't part of the original plan, but they're the kind of bugs that only surface once you push a new code path hard enough to hit its edges, and each one makes the implicit multirate machinery a bit more solid.
