Refactoring 3000+ Lines into Generic Tableaus

May 7, 202615 min readGSoC Updates

OrdinaryDiffEq.jl is one of the most comprehensive ODE solver libraries ever built. It implements over 300 algorithms spanning explicit, implicit, exponential, symplectic, and multirate methods. But this comprehensiveness has a cost: code duplication.

This post examines the duplication problem in detail, explains the generic tableau architecture being built to solve it, and discusses the engineering trade-offs involved in refactoring performance-critical numerical infrastructure without breaking anything.

The Duplication Problem

Consider the explicit Runge–Kutta family. An \(s\)-stage ERK method computes:

$$k_i = f\!\left(t_n + c_i h,\; y_n + h \sum_{j=1}^{i-1} a_{ij} k_j\right), \qquad i = 1, \ldots, s$$

$$y_{n+1} = y_n + h \sum_{i=1}^{s} b_i k_i$$

Every ERK method — RK4, Tsit5, DP5, Vern6, Feagin10 — implements this same mathematical structure. The only difference is the Butcher tableau coefficients \((A, b, c)\). Yet in the codebase, each has its own perform_step!:

# In the current codebase, each method has its own function:
# perform_step!(integrator, cache::RK4Cache, ...)        ~80 lines
# perform_step!(integrator, cache::Tsit5Cache, ...)      ~120 lines
# perform_step!(integrator, cache::DP5Cache, ...)        ~150 lines
# perform_step!(integrator, cache::Vern6Cache, ...)      ~200 lines
# perform_step!(integrator, cache::Feagin10Cache, ...)   ~350 lines
# ... and many more
#
# Total: ~3,300 lines of structurally identical code

Each implementation unpacks coefficients, evaluates stages, accumulates contributions, and updates the solution — all following the same pattern. The differences are limited to:

  1. The number of stages \(s\)
  2. The specific coefficient values
  3. Whether the method has FSAL (First Same As Last) property
  4. Whether an embedded error estimator is used (and its coefficients)

Why This Matters

Code duplication in a numerical library is more than just an aesthetic problem:

  • Bug propagation: A bug in the stepping logic must be fixed in every method individually. A subtle off-by-one error in the FSAL handling of Tsit5 wouldn't automatically be fixed in Vern6.
  • Maintenance burden: Any architectural change to the integrator (e.g., changing the cache structure, adding a new callback hook) requires modifying dozens of files.
  • Barrier to contribution: New contributors who want to add a method must duplicate hundreds of lines of boilerplate rather than just specifying tableau coefficients.
  • Testing complexity: Each method needs its own convergence tests, making the test suite large and slow.

The Generic Tableau Architecture

The solution is to define a single, parametric tableau type and a single perform_step! that dispatches on the tableau:

"""
    GenericERKTableau{s, T}

Generic explicit Runge-Kutta tableau with `s` stages and
coefficient type `T`. The stage count is a type parameter
to enable compile-time loop unrolling.
"""
struct GenericERKTableau{s, T <: Real}
    A::SMatrix{s, s, T}          # Butcher matrix (strictly lower triangular)
    b::SVector{s, T}             # Weights
    bhat::SVector{s, T}          # Embedded error estimator weights
    c::SVector{s, T}             # Nodes
    fsal::Bool                   # First Same As Last property
    order::Int                   # Method order
    error_order::Int             # Embedded estimator order
end

The key design decision is making the stage count s a type parameter. This allows Julia's compiler to:

  • Unroll the stage loops: for i in 1:s becomes a sequence of inlined operations when s is known at compile time
  • Specialize the cache: The number of pre-allocated stage vectors is determined at compile time
  • Eliminate dead branches: FSAL-specific code can be compiled away for non-FSAL methods

The Generic perform_step!

function perform_step!(integrator, cache::GenericERKCache)
    @unpack t, dt, u, p, f = integrator
    @unpack tab, K, utmp = cache
    s = nstages(tab)

    # Stage evaluations
    @inbounds for i in 1:s
        # Compute stage argument: u + dt * sum(A[i,j] * K[j])
        @. utmp = u
        for j in 1:i-1
            if !iszero(tab.A[i, j])
                @. utmp += dt * tab.A[i, j] * K[j]
            end
        end
        # Evaluate f at the stage point
        f(K[i], utmp, p, t + tab.c[i] * dt)
    end

    # Update solution: u_new = u + dt * sum(b[i] * K[i])
    @. integrator.u = u
    @inbounds for i in 1:s
        if !iszero(tab.b[i])
            @. integrator.u += dt * tab.b[i] * K[i]
        end
    end

    # Error estimation (for adaptive stepping)
    if has_embedded(tab)
        @. cache.atmp = zero(eltype(u))
        @inbounds for i in 1:s
            @. cache.atmp += dt * (tab.b[i] - tab.bhat[i]) * K[i]
        end
        integrator.EEst = integrator.opts.internalnorm(cache.atmp, t)
    end
end

This single function replaces ~3,300 lines of hand-written stepping code. Adding a new ERK method now reduces to defining its tableau coefficients:

# Adding a new method is just defining coefficients:
function Ralston4Tableau(T = Float64)
    A = @SMatrix T[
        0       0        0       0
        0.4     0        0       0
        0.29698 0.15875  0       0
        0.21827 -3.05097 3.83274 0
    ]
    b = @SVector T[0.17476, -0.55149, 1.20553, 0.17118]
    c = @SVector T[0.0, 0.4, 0.45573, 1.0]
    GenericERKTableau{4, T}(A, b, b, c, false, 4, 3)
end

Performance: The Critical Constraint

The entire refactoring is predicated on one constraint: zero performance regression. SciML solvers are used in production scientific computing workflows where even a 5% slowdown is unacceptable.

We validate performance using BenchmarkTools.jl and the allocation-checking framework AllocCheck.jl:

using BenchmarkTools, OrdinaryDiffEq

# Lorenz system benchmark
function lorenz!(du, u, p, t)
    σ, ρ, β = p
    du[1] = σ * (u[2] - u[1])
    du[2] = u[1] * (ρ - u[3]) - u[2]
    du[3] = u[1] * u[2] - β * u[3]
end

u0 = [1.0, 0.0, 0.0]
p = (10.0, 28.0, 8/3)
prob = ODEProblem(lorenz!, u0, (0.0, 100.0), p)

# Compare handwritten vs. generic
@btime solve($prob, Tsit5());           # Handwritten: ~X μs
@btime solve($prob, GenericTsit5());    # Generic:     ~Y μs (target: within 2%)

The key to achieving performance parity is type-parametric tableaus. When the stage count is a type parameter, Julia's aggressive specialization eliminates all abstraction overhead at compile time. The generated LLVM IR for the generic version is effectively identical to the handwritten version.

Migration Strategy

We're migrating solvers in phases, ordered by structural complexity:

PhaseFamilyMethodsLines Removed
1Explicit RK (non-FSAL)RK4, Ralston4, etc.~400
2Explicit RK (FSAL)Tsit5, DP5, BS3, etc.~800
3DIRK / SDIRKImplicitEuler, TRBDF2, etc.~600
4IMEX-RK (ARK)KenCarp3/4/5, etc.~900
5Symplectic / Low-storageLSRK, SymplecticRK~600

Each phase follows a strict protocol:

  1. Implement the generic tableau and stepping function
  2. Verify convergence order via method-of-manufactured-solutions tests
  3. Benchmark against the handwritten version (must be within 2%)
  4. Check allocations via AllocCheck.jl (must be zero-allocation)
  5. Deprecate the old implementation (keeping it available for one release cycle)
  6. Remove the old code in the following release

Lessons Learned So Far

  • Type parameters are essential for performance in generic numerical code. Without compile-time stage counts, the inner loops can't be unrolled and performance drops 10–30%.
  • Incremental migration is safer than a big-bang rewrite. Each method is migrated and validated independently.
  • Existing tests are invaluable. SciML's extensive test suite catches subtle numerical bugs that would be invisible in simple benchmarks.
  • User-facing API must not change. solve(prob, Tsit5()) should work exactly as before — the refactoring is entirely internal.
