Lessons from Contributing to SciML

May 7, 20269 min readOpen Source

Over the past several months, I've merged 16+ pull requests across three SciML repositories: OrdinaryDiffEq.jl, SciMLBenchmarks.jl, and ODEInterfaceDiffEq.jl. This post distills the lessons I've learned about contributing to a large-scale scientific open-source ecosystem — lessons about code, collaboration, and the culture of rigorous numerical software.

1. The Best Way to Learn is by Doing

When I started contributing in January 2026, I didn't spend months just reading code. I jumped straight into writing it, starting with validation and benchmark code before moving into the core solvers. By actively working on the codebase, I rapidly picked up:

  • How the entire perform_step! pipeline is constructed
  • The cache allocation pattern and how alg_cache dispatch works
  • The integrator loop structure (loopheader!, perform_step!, loopfooter!)
  • The test suite structure and convergence testing methodology

This hands-on approach forced me to learn fast. Breaking the tests and fixing them taught me more about the rationale behind design decisions — like why caches are parametric types, or why FSAL is handled as a separate code path — than reading ever could have.

2. Numerical Testing Is Different From Software Testing

In most software, a test checks "does this function return the expected output?" In numerical computing, the answer is almost never exact. Instead, we test:

# Convergence order test: The GOLD STANDARD
# Verify that the method achieves its theoretical order of accuracy
for dt in [1/2^n for n in 2:8]
    sol = solve(prob, MyMethod(), dt=dt, adaptive=false)
    err = norm(sol.u[end] - exact_solution)
    # Error should scale as O(dt^p) where p is the method order
    push!(errors, err)
end

# Compute empirical convergence order
for i in 2:length(errors)
    order = log(errors[i-1] / errors[i]) / log(2)
    @test order ≈ expected_order atol=0.3
end

Key numerical testing patterns I learned:

  • Convergence order verification: The method must achieve its theoretical order on smooth problems. This catches coefficient errors that wouldn't cause outright failures.
  • Work-precision diagrams: Plot error vs. computational cost (time or function evaluations) to verify the method is efficient, not just correct.
  • Stiff problem batteries: Run on standard stiff benchmarks (Van der Pol, HIRES, Robertson) to verify stability properties.
  • Regression tests: Compare against known-good solutions to catch subtle regressions.

3. Performance Is a Correctness Requirement

In SciML, a solver that produces correct results but is 2x slower than expected is considered buggy. Performance is not an optimization to do later — it's a design constraint from day one.

Every PR I submit includes:

  • Allocation check: perform_step! must be zero-allocation (verified via AllocCheck.jl)
  • Benchmark comparison: Must not regress vs. existing methods on standard problems
  • Type stability: @code_warntype must show no Any or Union types in the hot path

I once submitted a PR where a seemingly harmless array creation in the cache initialization caused a 15% performance regression due to an extra GC cycle during long integrations. Chris caught it in review. Lesson learned: profile everything, assume nothing.

4. The Art of Incremental PRs

My biggest mistake early on was trying to do too much in a single PR. A PR that implements 16 new LSRK methods, adds their tests, and refactors the cache structure is impossible to review effectively.

What I learned to do instead:

  1. PR 1: Add the tableau coefficients and type definitions
  2. PR 2: Implement perform_step! for the simplest variant
  3. PR 3: Add convergence tests
  4. PR 4: Extend to the full family of methods
  5. PR 5: Add benchmarks and documentation

Each PR is small, focused, and independently verifiable. Reviewers can give detailed feedback on each step rather than rubber-stamping a massive diff.

5. Starting with Benchmarks and Validation

Between January and March, my initial focus was entirely on SciMLBenchmarks.jl and DAE benchmark infrastructure. While it might seem less exciting than new solver implementations, it was the perfect entry point. Benchmarks:

  • Define the standard: A benchmark establishes what "correct" looks like for a given problem class
  • Force you to understand performance: You learn to read work-precision diagrams and spot performance regressions
  • Catch edge cases: Automated benchmark runs detect when a change breaks under stress
  • Expose the internals: To benchmark a solver, you have to understand how it's called and what it's trying to optimize

The 8 DAE benchmarks I contributed — including the Car Axis Index-3 system, Andrews' Squeezing Mechanism, and the Slider-Crank Mechanism — taught me how numerical software is validated in the real world. This validation work built the foundation I needed to start writing the solvers themselves.

6. Communication Patterns That Work

SciML maintainers are busy researchers. Effective communication is concise and context-rich:

  • Issue before PR: For non-trivial changes, open an issue first to discuss the approach. This prevents wasted effort on rejected designs.
  • PR descriptions that tell a story: Not just "what changed" but "why" and "what was considered and rejected."
  • Respond to reviews promptly: Stale PRs lose momentum. Address feedback within 24-48 hours.
  • Ask specific questions: "Should I use SDIRK or ESDIRK structure for the implicit tableau?" is better than "How should I do this?"

7. Scientific Software Has Unique Challenges

Contributing to SciML taught me that scientific software operates under constraints not found in typical web/app development:

  • Mathematical correctness: A typo in a coefficient isn't a cosmetic bug — it changes the convergence order and can produce silently wrong results
  • Backward compatibility: Researchers have published papers using specific solver configurations. Changing default behavior can invalidate published results.
  • Cross-type generality: Code must work with Float64, BigFloat, Dual numbers (autodiff), Measurement (uncertainty propagation), and custom types.
  • Long-running correctness: A bug that only manifests after 10 million time steps is much harder to catch than one that fails immediately.

8. The Value of Persistence

Not every PR is merged on the first try. My Rosenbrock23/32 refactoring PR (#3273) went through 4 rounds of review over several weeks, each time requiring significant changes. The MREEF multirate implementation (#3139) required deep discussions about the solver interface.

The key is to treat review feedback as a learning opportunity, not criticism. Every piece of feedback from experienced maintainers like Chris, Kanav, or Oscar is worth more than hours of independent study.

Key Takeaways

  1. Learn by implementing — start with benchmarks and work your way into the core
  2. Numerical correctness requires specialized testing beyond unit tests
  3. Performance (allocations, type stability) is a design constraint, not an afterthought
  4. Small, focused PRs get reviewed faster and merged more reliably
  5. Benchmarks are the perfect training ground for understanding solver internals
  6. Communication matters as much as code quality
  7. Scientific software has unique correctness requirements
  8. Persistence through review cycles builds both code quality and developer skill
