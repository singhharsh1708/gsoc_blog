Zero Allocation Programming in Julia

📅 May 7, 2026🕐 12 min readJulia Performance

In numerical computing, memory allocation is often the dominant performance bottleneck. Every heap allocation triggers garbage collection (GC) pressure, disrupts cache locality, and introduces unpredictable latency. For solver inner loops that execute millions of times, even a single allocation per step can be devastating.

This post covers the techniques I use daily when writing solver code for OrdinaryDiffEq.jl — practical patterns for achieving zero-allocation hot paths in Julia.

1. Why Allocations Matter

Let's start with a concrete example. Consider computing a vector update in a Runge–Kutta stage:

# BAD: Creates a new temporary array every call
function update_stage_bad(u, dt, a, k1, k2, k3)
    return u + dt * (a[1] * k1 + a[2] * k2 + a[3] * k3)
    # ↑ Each + and * creates a new temporary array
    # This single line allocates 5 temporary vectors!
end

# GOOD: In-place update with broadcast fusion
function update_stage_good!(utmp, u, dt, a, k1, k2, k3)
    @. utmp = u + dt * (a[1] * k1 + a[2] * k2 + a[3] * k3)
    # ↑ The @. macro fuses everything into a single loop
    # Zero allocations, zero temporaries
    return nothing
end

The @. (broadcast fusion) macro is Julia's most powerful tool for eliminating allocations. It transforms the expression into a single fused loop that computes element-by-element, writing directly into the destination array.

using BenchmarkTools
n = 10_000
u = randn(n); k1 = randn(n); k2 = randn(n); k3 = randn(n)
utmp = similar(u); a = [0.3, 0.5, 0.2]; dt = 0.01

@btime update_stage_bad($u, $dt, $a, $k1, $k2, $k3);
# 12.4 μs (5 allocations: 390.72 KiB)

@btime update_stage_good!($utmp, $u, $dt, $a, $k1, $k2, $k3);
# 2.1 μs (0 allocations: 0 bytes)
# ~6x faster due to zero allocations and better cache usage

2. The Cache Pattern

The fundamental pattern in OrdinaryDiffEq.jl is the pre-allocated cache. All temporary arrays needed during a step are allocated once during solver initialization and reused at every step:

struct MySolverCache{uType, rateType}
    # Pre-allocated working arrays
    k1::rateType        # Stage derivatives
    k2::rateType
    k3::rateType
    k4::rateType
    utmp::uType         # Temporary for stage argument
    atmp::uType         # Temporary for error estimation
end

function alg_cache(alg::MySolver, u, ...)
    # Allocate ONCE during init — never again
    k1 = zero(u)
    k2 = zero(u)
    k3 = zero(u)
    k4 = zero(u)
    utmp = zero(u)
    atmp = zero(u)
    MySolverCache(k1, k2, k3, k4, utmp, atmp)
end

function perform_step!(integrator, cache::MySolverCache)
    @unpack k1, k2, k3, k4, utmp = cache
    # All operations use pre-allocated arrays
    # No allocations in the hot path
    @. utmp = integrator.uprev + integrator.dt * k1
    integrator.f(k2, utmp, integrator.p, integrator.t)
    # ...
end

3. Views Instead of Copies

Array slicing in Julia creates copies by default. For sub-array operations, use @view to create zero-copy references:

# BAD: Creates a copy of the sub-array
function process_component_bad(u, n)
    x = u[1:n]           # Allocates a new array of size n
    y = u[n+1:2n]        # Allocates another new array
    return dot(x, y)
end

# GOOD: Zero-copy views
function process_component_good(u, n)
    x = @view u[1:n]     # No allocation — just a pointer + bounds
    y = @view u[n+1:2n]  # No allocation
    return dot(x, y)
end

n = 5000; u = randn(2n)
@btime process_component_bad($u, $n);   # 3.2 μs (2 allocations: 78.17 KiB)
@btime process_component_good($u, $n);  # 1.8 μs (0 allocations: 0 bytes)

4. StaticArrays for Small Fixed-Size Problems

For problems with small state vectors (roughly up to 100 elements), StaticArrays.jl provides stack-allocated arrays that bypass the heap entirely:

using StaticArrays

# Standard array — heap allocated
function lorenz_heap(u, p, t)
    σ, ρ, β = p
    du1 = σ * (u[2] - u[1])
    du2 = u[1] * (ρ - u[3]) - u[2]
    du3 = u[1] * u[2] - β * u[3]
    return [du1, du2, du3]      # ← Heap allocation every call!
end

# SVector — stack allocated, zero GC pressure
function lorenz_static(u, p, t)
    σ, ρ, β = p
    du1 = σ * (u[2] - u[1])
    du2 = u[1] * (ρ - u[3]) - u[2]
    du3 = u[1] * u[2] - β * u[3]
    return SVector(du1, du2, du3)  # ← Stack allocated, zero cost
end

u0_heap = [1.0, 0.0, 0.0]
u0_static = SVector(1.0, 0.0, 0.0)
p = (10.0, 28.0, 8/3)

@btime lorenz_heap($u0_heap, $p, 0.0);     # 31 ns (1 allocation: 80 bytes)
@btime lorenz_static($u0_static, $p, 0.0);  # 3.1 ns (0 allocations: 0 bytes)
# 10x faster!

The OOP (out-of-place) path in OrdinaryDiffEq.jl — the ConstantCache variant — is designed specifically for StaticArrays. When you use SVector state, the entire integration runs without a single heap allocation.

5. @inbounds and @simd

Julia performs bounds checking on every array access by default. In performance-critical inner loops where indices are guaranteed valid, @inbounds eliminates this overhead:

# Explicit stage accumulation with performance annotations
function accumulate_stages!(utmp, u, dt, A, K, stage, s)
    @inbounds @simd for idx in eachindex(utmp)
        val = u[idx]
        for j in 1:stage-1
            val += dt * A[stage, j] * K[j][idx]
        end
        utmp[idx] = val
    end
end

Important caveats:

  • @inbounds removes safety checks — using it with invalid indices causes undefined behavior (segfaults, silent data corruption)
  • Use eachindex(A) to iterate — this guarantees valid indices and often lets the compiler prove bounds safety automatically
  • @simd only helps for loops with independent iterations and simple arithmetic — the compiler must be able to vectorize
  • Always benchmark before and after to verify the improvement is real

6. Verifying Zero Allocations with AllocCheck.jl

In the SciML ecosystem, we use AllocCheck.jl as a CI-enforced check to ensure perform_step! remains allocation-free:

using AllocCheck

# Check that perform_step! allocates nothing
allocs = check_allocs(perform_step!,
    (typeof(integrator), typeof(cache)))

if !isempty(allocs)
    println("ALLOCATION DETECTED in perform_step!:")
    for a in allocs
        println("  $(a.type) at $(a.backtrace[1])")
    end
    error("perform_step! must be zero-allocation!")
end

This runs as part of CI for every PR. If a new method introduces even one allocation in its perform_step!, the CI fails and the PR cannot be merged.

7. Common Allocation Traps

TrapSolution
A[1:n, :] (array slice)@view A[1:n, :]
u + dt * k (creates temp)@. utmp = u + dt * k
[a, b, c] (array literal)SVector(a, b, c) or pre-allocate
String interpolation in hot loopRemove or guard with if verbose
Closures capturing mutable statePass as function arguments instead
Type-unstable containersParametric types with concrete type params
map(f, collection) (creates new array)map!(f, dest, collection)

8. Real-World Impact

Here's a comparison solving the Lorenz system for 1000 time units with Tsit5, showing the impact of allocation-free code:

using OrdinaryDiffEq, BenchmarkTools

prob_heap = ODEProblem(lorenz_heap, [1.0, 0.0, 0.0], (0.0, 1000.0), p)
prob_static = ODEProblem(lorenz_static, SVector(1.0, 0.0, 0.0), (0.0, 1000.0), p)

@btime solve($prob_heap, Tsit5(), save_everystep=false);
# ~1.2 ms, 45,000+ allocations, ~3.5 MiB

@btime solve($prob_static, Tsit5(), save_everystep=false);
# ~0.15 ms, 0 allocations, 0 bytes
# 8x faster, zero GC pressure

For long-running simulations, the zero-allocation version maintains consistent performance without GC pauses, while the allocating version exhibits periodic latency spikes as the garbage collector runs.
